
- Pro-wide tools (address book, tutorial, help) live in the /pro space via ProSidebar + ProSupportHost; per-wedding tools stay inside each wedding's dashboard — the pro picks a wedding first.
- Wedding collaboration: invited couples are linked via `wedding_collaborators` + `is_wedding_collaborator()`; editable modules get FOR ALL policies, others SELECT-only, so read-only is enforced by RLS — and shared-module queries filter on `wedding_id` (not `user_id`) when a wedding is selected.
- Per-member Jour J links reuse the public planning URL with `?membre=<team id>`; no extra token — keeps the simple clickable-link sharing.
- Guest page (RSVP) theming lives in `wedding_rsvp_events.customization` with preset palettes/fonts from `src/data/guestPageThemes.ts`; never free-form CSS, to keep mobile layout safe.
- Collaboration direction is encoded in wedding_collaborators.role: 'couple' (pro invites couple, Jour J read-only for the couple) or 'planner' (couple invites pro onto the couple's wedding, full edit via is_wedding_planner_collaborator) — so existing couple data is shared, never overwritten.
- Invited couples (role 'couple') see only the pro's shared wedding; they edit budget, guests/RSVP, seating, drinks and accommodations, other modules are greyed — keeps one coherent view without deleting their own default wedding.
- Organisation → Jour J links: vendor-tracking status sync (checklist task / Jour J team) runs in a DB trigger on `vendors_tracking_preprod` so every entry point is covered; seating/drinks/decor/trombinoscope validations are stored in `wedding_jour_j_handoffs` and read live in Mon Jour J (no exported copies), and the trombinoscope reaches `coordination_team` only via the `sync_key_people_to_jour_j` RPC because invited couples cannot write the pro's team.
- Jour J step completion lives in `coordination_planning.status` ('pending'|'completed'), toggled from the Conducteur tab; the public planning refreshes via realtime plus a 20 s poll because anonymous viewers may not receive realtime events.
- Budget deposits live in `budgets_detail.payment_schedule` (jsonb: up to 3 installments + cash_day); paid installments drive the deposit column and cash_day feeds the Jour J envelopes. The daily `budget-deposit-reminders` edge function (pg_cron) emails the owner and collaborators — keeps one budget module for couples and pros.
- Ceremony planning (religious/civil) is stored per wedding in `wedding_ceremony_plans.data`; owner and planner collaborators edit, couple collaborators read only — matches the shared-module rights matrix.
- Photo-list "done" ticks are a separate `coordination_documents` row (category `photo_list_status`) so the Conducteur never overwrites the list editor.
- Pro client forms (`pro_client_forms` + `pro_client_form_responses`) are reached anonymously only through the `get_public_client_form` / `submit_client_form_response` RPCs by share token; each response stores a `questions_snapshot` so later question edits never break old one-pagers.
- Pro plans: profiles.subscription_type 'pro_premium' = Organisation complète, 'pro_jour_j' = Coordination Jour J (Jour J-only weddings); set by stripe-webhook from create-pro-checkout metadata (Stripe product IDs live in that function) — the 30-day trial stays card-free via ProTrialGate.
- Music (DJ) and Catering modules store their content as one jsonb row per wedding in `wedding_module_plans` (module 'music'|'catering'), editable by owner and all collaborators; the DJ sheet reaches Jour J as a PDF in `coordination_documents` (category organisation-music) — one generic table keeps new shared modules cheap.
- Supplied November blog articles use slug-scoped presentation overrides shared with prerendered heads; this preserves their final CTA and image alt without changing other articles or the database schema.
- SEO prerender: scripts/prerenderHeads.ts fetches published blog_posts and visible prestataires_rows from Supabase at build and writes full HTML + JSON-LD for every sitemap URL — AI crawlers don't run JS; new content is covered on next publish.
